## 一、需求分析

### 1.1 要解决的问题

"服务能启动"不等于"能稳定运行"。没有指标时，运维只能在用户报错后翻日志猜。
有了指标，才能回答三个问题：**何时变慢、影响多大、哪个组件异常**。

### 1.2 需求拆解

| --- | --- | --- |
| R1 | 应用能运行并暴露 `/metrics` | 真实运行，原始文本为证 |

| R3 | 标签不含用户 ID、原始 URL 等高基数值 | 4 条测试强制 |

## 二、设计决策

### 2.1 决策一：应用只暴露原始累计值，速率和分位数交给 Prometheus

| 谁 | 算什么 |
| --- | --- |
| 应用 | 只 `inc()` 和 `observe()`，暴露原始 Counter / Histogram |
| Prometheus | 用 `rate()` 算速率、`histogram_quantile` 算分位数 |

**为什么不自己算**：

1. 应用算的瞬时值**没法回溯**——服务重启就丢历史。
2. "每秒多少"依赖采样窗口。应用自己算等于把窗口选择权藏起来了，
   而窗口选择本身就是个分析决策（见 2.4）。
3. 预聚合会把分辨率永久性地损失掉。

### 2.2 决策二：模板路由做标签（本实验最重要的一条）

```
✅ route="/api/items/{item_id}"   → 取值数量 = 路由数量
❌ route="/api/items/1"           → 取值数量 = 数据行数
```

标签基数按**乘积**增长：`|method| × |route| × |status|`。
本应用 `7 × 8 × 20 ≈ 1120` 条；换成原始 URL 就是百万级。
后果链条是：内存爆 → 查询超时 → `/metrics` 变长 → 抓取超时 →
**Prometheus 自己被压垮**。

所以 `yuchuli_lu_you()` 取不到路由时返回固定字符串 `"unmatched"`，
**绝不回退到 `request.url.path`**。

### 2.3 决策三：延迟用 Histogram，桶边界压在告警阈值上

平均值会稀释长尾（99×10ms + 1×2000ms → 平均 29.9ms，但 1% 用户等了 2 秒）。

桶边界 `(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, **1.0**, 2.0, 5.0)`
里的 **1.0 是刻意放的**——告警阈值就是 1 秒。
桶边界没压在阈值上的话，"p95 > 1" 实际是在 0.5 和 2.0 之间跳，告警会很迟钝。

### 2.4 决策四：不同指标用不同窗口

| 指标 | 窗口 | 理由 |
| --- | --- | --- |
| 请求速率 | 1m | 纯计数，不受比例影响；短窗口能看出瞬时变化 |
| 错误率 | 5m | 比例类，低流量下 1m 窗口分母太小会剧烈抖动 |
| p95 | 5m | 分位数越短越不稳定 |

测试 `test_shijian_chuangkou_buyao_guoduan` 强制所有窗口 ≥ 30s——
15s 抓取间隔下 30s 窗口只有 2 个样本，`rate()` 的线性外推不可靠。

### 2.5 决策五：告警阈值必须写依据

指导书原文："先解释阈值来自何处，不用一次尖峰触发。"

所以每条告警的 `shuoming` 里都有「阈值依据」段落，做法是拿
**正常基线**和**受控实验能达到的水平**卡区间：

| 告警 | 正常基线 | 受控实验水平 | 阈值 |
| --- | --- | --- | --- |
| 错误率 | 0% | 50%（`/api/error?rate=1`） | **5%** |
| p95 | 约 10ms | 500ms~2s（`/api/slow`） | **1s** |
| 进程内存 | 60~90MB | — | 512MB（约 5 倍余量） |
| 进程 CPU | < 0.2 核 | — | 0.8 核 |

**全部告警都带 `for`**（1m~5m）。没有 `for` 的告警会被一次瞬时尖峰触发，
用不了多久就没人看了——测试 `test_meitiao_guize_dou_you_for` 强制这一点。

### 2.6 决策六：Windows 进程指标自己补

`prometheus_client` 的 `ProcessCollector` 面向 Linux，
原生 Windows 上不提供 `process_cpu_seconds_total` 和
`process_resident_memory_bytes`。用 psutil 自建 collector，
**只在 win32 注册**（Linux 上已有的会重名冲突）。

**口径必须写清楚**：这里量的是**当前应用进程**，不是整机。
整机要用 node_exporter，容器要用 cAdvisor，三种口径不能混在一张图上比。

### 2.7 决策七：Dashboard 从零设计，不导入社区面板

指导书："现成面板导入不等于自主设计。"

10 个面板每一个的 `description` 里都写了它回答什么运维问题。
测试 `test_meige_mianban_dou_shuoming_ta_huida_de_wenti` 强制检查——
没写 description 的面板，三个月后的自己也看不懂为什么要有它。

## 三、实现要点

### 3.1 埋点中间件

```python
@app.middleware("http")
async def zhibiao_zhongjianjian(request, call_next):
    if request.url.path == "/metrics":
        return await call_next(request)      # ③ 自我污染
    kaishi = time.perf_counter()
    ZHENGZAI_CHULI.inc()
    ma = 500
    try:
        xiangying = await call_next(request)
        ma = xiangying.status_code
        return xiangying
    finally:
        ZHENGZAI_CHULI.dec()
        lu_you = yuchuli_lu_you(request)     # ★ 必须在 call_next 之后取
        HTTP_QINGQIU_ZONGSHU.labels(method=..., route=lu_you, status=str(ma)).inc()
        HTTP_YANCHI.labels(method=..., route=lu_you).observe(time.perf_counter() - kaishi)
```

三个关键设计点：

| 点 | 为什么 |
| --- | --- |
| 用 `finally` 而不是 `except` | 异常请求也要计 5xx。只在正常路径计数的话，**服务开始报错时指标反而看不见错误** |
| `ma` 初始化为 500 | 异常时 `call_next` 会抛，`ma` 保持 500，计数正确 |
| 路由在 `call_next` **之后**取 | 见下面的坑 |

#### ★ 踩过的坑：中间件在路由之前运行

第一版在 `call_next` 之前取 `request.scope["route"]`：

```python
lu_you = yuchuli_lu_you(request)   # ❌ 这里 scope["route"] 还是 None
xiangying = await call_next(request)
```

因为中间件包在整个应用外面，`call_next` 之前 Starlette 还没做路由匹配，
`scope["route"]` 是 `None` —— 于是**所有请求的 route 标签都是 `unmatched`**，
模板路由完全失效，高基数控制也就无从谈起（所有请求挤在一条序列里，
看起来"基数很低"，但那是假象）。

暴露方式：`test_qingqiu_jishu_zengjia` 报 `assert 0.0 == 1.0`。
代码里没有报错，只是计数全跑到 `unmatched` 上去了。

修法：把路由取值挪到 `call_next` 之后的 `finally` 里。

**这个坑值得记下来**：① 中间件的执行时机和路由匹配的先后关系
② "标签值不对"不会报错，只会让数据静默错位。

### 3.2 高基数控制工具

```python
def yuchuli_lu_you(request):
    route = request.scope.get("route")
    if route is None:
        return "unmatched"
    return getattr(route, "path", "unmatched")

def yanchi_fen_tong(haomiao):
    """把毫秒归到 6 个桶名里，不用具体毫秒数当标签。"""
    ...
```

实测验证（真实 `/metrics` 输出）：

```
http_requests_total{method="GET",route="/api/items",status="200"} 1.0
http_requests_total{method="GET",route="/api/items/{item_id}",status="200"} 2.0
```

访问 `/api/items/1` 和 `/api/items/2` 只产生**一条**序列。

### 3.3 500 响应不泄露堆栈

统一异常处理器只返回一句"服务器内部错误"，**不返回异常原文**——
那会泄露文件路径、库版本、SQL 片段。排障要看日志，不是看响应体。
测试 `test_500_xiangying_bu_baolu_duizhan` 断言响应里搜不到异常文本。

### 3.4 Grafana provisioning

数据源和 Dashboard 都用文件管理，不用界面点。理由：
① 手工配的存进 Grafana 数据库，换机器就没了；
② 文件能进 Git、能被复核。

`allowUiUpdates: false` 是刻意的——否则会出现"界面上改了、文件没变、
换台机器就丢了"的经典问题。要改 Dashboard 就改 JSON 文件。

数据源 `uid` 固定为 `prom-demo`，Dashboard JSON 里引用的就是它。
不固定的话换机器导入会对不上（测试 `test_mianban_yinyong_de_shuju_yuan_uid_cunzai` 盯这个）。

## 六、问题与反思

### 6.1 最深的一条体会：监控自己也会崩

以前我把"加监控"默认当成纯粹的好事。做这个实验时想清楚一件：
**高基数标签会先把 Prometheus 自己压垮**。

标签基数是乘积关系。"多加一个标签"看着只是加一列，
实际上是把基数乘以一个新维度。用完原始 URL 做标签，10 万商品就是 1400 万条序列。

所以"埋点"不是"能埋就埋"，**每个标签都要先问一句取值数量上限是多少**。
这条纪律本实验用了 4 条测试来强制。

### 6.2 中间件时机的坑

3.1 节那个坑的教训是：**"标签值不对"不会报错，只会让数据静默错位。**

当时所有请求都归到 `unmatched` 一条序列上。
如果不看测试，甚至会误以为"基数控制得很好"——
因为序列确实只有一条。**看起来很干净的数据也可能是错的。**

### 6.3 关于环境确认

实验03 和实验07 都因为"没先确认环境"浪费了时间，这次还是踩了：
应该在写第一行代码之前就跑一次 `Test-NetConnection` 确认能不能下载
Prometheus，而不是写完之后才发现装不上。

**这是三次重复犯的同一个错**，值得单独记一笔：
**环境确认应该是第 0 步，不是第 1 步。**

### 6.4 还没解决的

1. **Prometheus / Grafana 未实跑**（最大缺口）。
2. **没有 SLO / Error Budget 面板**。指导书把"p95 延迟与 SLO/Error Budget"
   列为可选扩展，本次没做。
3. **没有关联 ID / 日志 / 追踪入口**。指标只能回答"发生了什么"。
4. **单 worker 限制**。多进程下 prometheus-client 的默认 Collector 会各算各的。
5. **没有配通知渠道**。只做到 Firing，没有实际发出去。

## 七、思考题

**1. 为什么请求延迟通常用 Histogram 而不是只记录平均值？**

两个原因：

**① 平均值掩盖长尾。** 99 个 10ms + 1 个 2000ms，平均 29.9ms 看着正常，
但 1% 的用户等了 2 秒。用户感知的是分位数，不是平均值。

**② 平均值不可聚合。** 可以 `sum` 两个服务的请求数，
但不能直接平均两个服务的平均延迟（除非知道各自请求数）。
Histogram 的桶是 Counter，可以跨实例相加后再算分位数。

还有一点容易错：**不能对算好的分位数再取平均**。
`avg(p95_A, p95_B) ≠ p95(全部)`。必须用 `histogram_quantile`
从聚合后的桶重新算。

**2. 标签基数过高会怎样影响内存、查询和系统可用性？**

基数按标签取值数量的**乘积**增长。后果链条：

1. **内存**：每条序列要维护索引和倒排表 → 内存爆。
2. **查询**：`sum(rate(...))` 要遍历所有匹配序列 → 超时。
3. **抓取**：`/metrics` 文本变长 → 抓取变慢 → 可能超时。
4. **可用性**：最坏情况 Prometheus OOM 被杀 → **监控整体失效**。

第 4 点最讽刺：**监控系统的崩溃往往是监控本身造成的**。
本应用 `7 × 8 × 20 ≈ 1120` 条序列完全可控；
换成原始 URL，10 万商品就是 1400 万条。

**3. `rate()` 的窗口选择过短或过长会分别掩盖什么现象？**

| 窗口 | 掩盖 | 放大 |
| --- | --- | --- |
| 过短 | 真实趋势；样本不足导致外推误差大 | 采样抖动、瞬时尖峰 |
| 过长 | 短时故障（被平均掉，看不到尖峰） | — |

本实验**按指标性质分别选**：请求速率用 1m（纯计数，能看瞬时变化），
错误率和 p95 用 5m（比例与分位数需要足够分母才稳定）。

并加了测试强制窗口 ≥ 30s——15s 抓取下 30s 只有 2 个样本，
`rate()` 的线性外推误差很大。

**4. CPU 升高与 p95 延迟升高同时出现时，为什么仍不能直接断言 CPU 是根因？**

相关性不等于因果。三种替代解释：

1. **共同原因**：下游变慢 → 请求排队 → 应用等待同时重试/自旋
   → CPU 和延迟同时涨。CPU 只是"陪着涨"。
2. **反向因果**：延迟高触发更多重试/重算，才把 CPU 推上去。
3. **巧合**：两个独立事件在同一时间窗发生（比如另一个进程在跑批）。

要定因果需要额外证据：**变更记录**（那段时间部署了什么）、
**火焰图/堆栈采样**、**把 CPU 压下去的对照实验**。

指标回答"发生了什么"，"为什么"需要更多信息源。这也是本实验
没有做日志和追踪关联而留下的缺口。

**5. 告警阈值应从固定经验值、历史基线还是 SLO 推导？不同选择适合什么场景？**

| 来源 | 适合 | 问题 |
| --- | --- | --- |
| 固定经验值 | 起步阶段，没历史数据 | 没有业务依据，容易定偏 |
| 历史基线（如"比上周高 3σ"） | 有稳定周期流量的系统 | 业务增长会被误判异常；大促必然误报 |
| **SLO 推导**（错误预算消耗速度） | 有明确可靠性目标的系统 | 要先定义 SLI/SLO，前期成本高 |

本实验用的是**基线 + 受控实验卡区间**的简化版（见 2.5 节的表），
不是拍脑袋，但也不是真正的 SLO。

**局限**：业务量或部署环境一变就必须重新标定。
真实系统应该走 SLO——先从"用户能接受多慢"反推错误预算，
再从预算消耗速度推阈值。
